## 会话与引擎选择（强制）

### 现状：会话来源有“两套体系”，必须分清


- **体系 A：FastAPI 依赖注入（推荐新代码优先使用）**
  - **入口**：`app/database/base.py:get_db`
  - **典型用法**：路由依赖 `Depends(get_db)` 或 `Depends(get_db_and_user)`（见 `app/utils/dependencies.py`）
  - **生命周期**：依赖生成 session，并在 `finally` 里关闭；异常时会 rollback（见 `get_db` 的实现）
  - **适用场景**：公开路由、需要显式事务边界/更易测试的接口、需要把 session 作为参数显式下传的 service/repo 设计

- **体系 B：中间件 + ContextVar（遗留兼容，谨慎使用）**
  - **入口**：`app/utils/auth_middleware.py` 会为鉴权路径创建 session，并用 `app/utils/db_session_context.py:set_db_session()` 写入 `ContextVar`
  - **典型用法**：仓储层（如 `app/repository/base_mapper.py`）通过 `app/utils/db_session_context.py:get_db_session()` 从上下文读取当前 session
  - **生命周期**：请求结束时中间件会调用 `reset_db_session()` 做清理（历史实现里包含“尝试 commit/rollback/close”，属于遗留行为）
  - **适用场景**：无法立即重构的遗留仓储调用链；短期内维持线上行为一致

- **后台任务 / 脚本（强制）**
  - **入口**：`app/database/base.py:get_db_session()`（`@asynccontextmanager`）
  - **原因**：该封装使用同步引擎 + `AsyncCompatibleSession`，用于避免 Celery/脚本里 `asyncio.run()` 场景下的事件循环绑定冲突（见函数注释）

### 强制：避免两套会话混用

- **同一条业务链路（同一次请求/同一个任务）尽量只使用一种体系**：
  - 若路由已注入 `db: AsyncSession = Depends(get_db)`，则 service/repo **优先显式接收并使用该 `db`**；
  - 若走遗留 ContextVar（BaseMapper 从上下文取 session），则路由层不应再额外创建“另一份 db”并在同一事务语义里交叉使用。
- **确有混用需求时（不推荐）**：必须在 PR 中说明原因，并给出“事务一致性”证明（同一写操作只落在一个 session；提交位置明确；异常时能正确回滚）。

### 强制：规避 `get_db_session` 命名冲突（必须用别名）

本项目同时存在两个不同语义的 `get_db_session`：

- `app.database.base.get_db_session`：**任务/脚本用** `@asynccontextmanager`
- `app.utils.db_session_context.get_db_session`：**请求上下文取值用**（ContextVar 读取）

为避免误导与误用，规则要求：

- **导入时必须显式起别名**（二选一或按需同时使用）：
  - 任务/脚本：
    - `from app.database.base import get_db_session as task_db_session`
  - 请求上下文（遗留）：
    - `from app.utils.db_session_context import get_db_session as ctx_db_session`

## 写操作事务规则（强制）

### 推荐规则（新代码强制）

- **写操作必须显式提交**：新增/更新/删除后需要显式 `commit`，并在异常路径显式 `rollback`
- **需要返回对象时**：按 `commit -> refresh -> 返回` 的顺序，避免返回脏数据/缺少自增字段

### 遗留兼容说明（不鼓励新增依赖）

- 由于历史原因，**体系 B（ContextVar）在请求结束阶段可能存在“统一尝试提交”的行为**（见 `app/utils/db_session_context.py:reset_db_session` 的注释/实现）。
- 规则要求：
  - **不要在业务代码里调用 `reset_db_session()`**（会话生命周期由中间件管理）
  - **不要依赖“请求结束自动提交”作为新增代码的事务方案**；新增写接口仍应遵循“显式 commit/rollback”的推荐规则（优先走体系 A）
  - **异常必须向上抛出**（不要吞异常后继续返回成功），避免出现“请求失败但部分写入被提交”的语义风险

## 多租户（tenant_id）规则（强制）

项目在 DB 层通过事件钩子对 `Select/Update/Delete` 自动注入 `tenant_id` 条件（见 `app/database/base.py:before_execute_handler`）。

- **必须**：仓储/服务设计时默认“租户隔离开启”，不要假设能查询到其它租户数据。
- **插入（Insert）必须处理 tenant_id**：自动注入仅覆盖 `Select/Update/Delete`；新增对象时需要在应用层写入正确的 `tenant_id`（通常来自 `app_runtime_context.get_tenant_id()`）。
- **禁止**：
  - 用 raw SQL / text 查询绕过租户条件
  - 在同一条查询里“重复注入 tenant 条件”导致语义错误（例如对子查询/别名错误追加）
- **注意（复杂查询的边界）**：
  - 复杂 JOIN/子查询/别名场景下，自动注入可能无法覆盖所有语义（或被字符串判断误判为“已注入”）
  - 对于关键读写路径：必须在 PR 中说明租户过滤是否依赖自动注入；如有不确定性，优先在仓储层显式加过滤并配套验证
- **需要跨租户/无租户查询**：
  - 必须在 PR 中明确说明业务理由、权限边界与审计策略
  - 实现上需要显式绕过时，必须提供最小化范围与防误用保护（例如仅管理员路径、仅特定表、仅统计聚合）

## 方言与兼容性

- 项目支持 MySQL / PostgreSQL，并包含达梦（DM）适配逻辑（见 `app/database/base.py`）。
- **新增模型字段/类型**需考虑跨库行为一致性：
  - JSON 字段：项目已做中文编码处理（`ChineseJSON`），不要另造一套 JSON 序列化策略
  - 时间/默认值：避免依赖单库特性

## 模型与索引规范（强制，来自团队约定）

- **模型**：
  - 必须继承 `baseModel`（自动包含 `id/tenant_id/created_at/updated_at/...`）
  - 必须使用 SQLAlchemy 2.0 风格的 `Mapped[...]` 类型注解
  - 字段必须包含中文 `comment`（状态枚举要把取值范围写清楚）
- **命名**：
  - 字段：`snake_case`（小写 + 下划线）
  - 布尔：`is_xxx/has_xxx/can_xxx`
  - 时间：`xxx_at`
- **索引**：
  - 统一放在 `__table_args__`
  - 命名：`idx_{表名}_{字段名}[_{字段名2}][_unique]`
  - 如按租户查询，必须考虑 `tenant_id` 索引（结合查询模式与表大小评估）
- **外键**：
  - ❌ 不创建外键约束（项目规范），需要在应用层保证数据一致性（删除/更新时自行校验与清理）

## 表结构变更交付物（不使用 Alembic）

- **禁止**引入或要求 Alembic（历史遗留：`alembic.ini`、`migrations/`、`app/database/migration_utils.py`）。
- **重要约束**：数据库结构变更由运维在客户现场手动执行；开发侧只提供脚本与说明，**不要在代码里自动执行迁移**。
- **必须提供（提测/上线材料中）**：
  - 升级 SQL（DDL/DML）
  - 回滚 SQL（可执行的 down 脚本；如不可回滚需写明原因与应急预案）
  - 变更说明（影响表、执行顺序、是否需要停机/锁表、验证 SQL）
  - 数据回填/迁移策略（幂等、可重试、耗时与锁表评估）
