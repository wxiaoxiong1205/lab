## 目标

让 AI 在本项目内**稳定产出可合并的改动**：先澄清需求与影响面，再按项目分层实现，最后用可验证的方式收口（含接口兼容、任务幂等、配置与租户隔离）。

## 必须遵守（强制）

- **先读后改**：改动任何模块前，先定位真实入口与调用链，至少阅读 2 处相关代码（路由/服务/仓储/模型/任务/配置之一）。
- **按分层放置代码**：
  - API：`app/api/v1/` 只做入参校验、鉴权/依赖、编排与返回结构
  - 业务：`app/services/`
  - DB 访问：`app/repository/`
  - 数据结构：`app/schemas/`（Pydantic）与 `app/models/`（SQLAlchemy）
- **不破坏租户隔离**：涉及 DB 查询/写入时，必须考虑 `tenant_id` 自动注入机制（见 `app/database/base.py` 的 `before_execute_handler`），避免绕过或重复注入导致语义错误。
- **异步一致性**：
  - FastAPI 请求链路（现状存在两种方式，必须分清并避免混用）：
    - 方式 A（依赖注入）：`app/database/base.py:get_db`（常见于公开路由、以及需要显式事务边界的接口）
    - 方式 B（遗留兼容）：`app/utils/auth_middleware.py` 为鉴权路径创建 DB session 并放入 `ContextVar`（`app/utils/db_session_context.py`），仓储层（如 `app/repository/base_mapper.py`）可能从上下文读取
  - 后台任务/脚本：优先使用 `app/database/base.py:get_db_session()`（同步引擎 + `AsyncCompatibleSession`），避免事件循环绑定冲突（见函数注释）
- **错误返回一致**：API 错误/校验错误需遵循项目的统一处理方式（参考 `app/main.py` 的 `validation_exception_handler` 与中间件链）。
- **配置即代码**：新增/变更配置必须同步更新 `env.example` 与 `app/core/config.py` 的校验逻辑（并保持默认值策略清晰）。
- **安全第一**：不得提交明文密钥、私有 URL、内部 IP；日志不得打印 token/密码/密钥/敏感业务数据。
- **方案先行**：新增功能/复杂改动必须先输出“技术方案”，经确认后再写代码（模板见下文“技术方案最小模板”）。


## 明确禁止（高危）

- **禁止**：在请求处理链路里 `asyncio.run()` / 新建事件循环；禁止在异步函数中直接用同步 DB 会话执行重 I/O。
- **禁止**：在路由层写复杂业务逻辑或直接拼 SQL；需要 SQL 时放到 `repository`，并保证租户/权限语义正确。
- **禁止**：新增绕过鉴权的敏感接口；调试用跨域/开放配置不得被当作生产方案。

## 关于 Alembic（重要）

- **本项目 Alembic 已废弃**：`alembic.ini`、`migrations/`、`app/database/migration_utils.py` 为历史遗留。
- **规则**：
  - 不要新增 Alembic revision，不要调用 Alembic CLI
  - **永远不要在代码中自动执行数据库迁移**
  - 不要以 Alembic 作为“表结构变更交付物”
- **表结构变更交付物（统一，运维执行）**：
  - 提供 **升级 SQL** + **回滚 SQL**
  - 提供 **执行说明**（执行顺序、是否需要停机/锁表、验证 SQL）
  - 写明 **兼容策略**（默认值/字段可空/数据回填）与 **回滚风险**

## 交付物清单（每次改动都要对齐）

- **需求说明**：改什么、为什么、影响哪些 API/任务/表/配置。
- **设计要点**：分层放置、关键边界、兼容策略。
- **实现**：代码改动（必要时含 SQL 变更与回滚脚本）。
- **验证**：最少提供一种可复现验证方式（单测/接口调用/脚本命令/日志证据）。
- **风险与回滚**：失败处理、幂等性与重试策略、回滚步骤。
