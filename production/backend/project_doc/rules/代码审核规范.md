# 代码审核规范

> 本规范供 GitLab CI AI 自动评审和人工评审共同使用。
> AI 评审只审核 MR Diff 中新增/修改/删除的代码，不审核已有未变更代码。

---

## 一、问题分级

| 级别 | 标识 | 定义 | 处理要求 |
|------|------|------|----------|
| 阻塞 | 🚨 | 安全漏洞、数据丢失/越权、租户隔离被绕过 | 必须修复后合并 |
| 安全 | 🔒 | 注入风险、硬编码密钥、路径穿越、敏感信息泄露 | 必须修复后合并 |
| 性能 | ⚡ | N+1 查询、无分页全表扫描、循环内 IO、资源未释放 | 强烈建议修复 |
| 重要 | ⚠️ | 违反项目规范、分层越界、会话混用、错误处理缺失 | 强烈建议修复 |
| 建议 | 💡 | 命名优化、可读性提升、注释补充、重复代码提取 | 可后续迭代 |

## 二、多租户与数据隔离（最高优先级）

本项目通过 `app/database/base.py:before_execute_handler` 对 Select/Update/Delete
自动注入 `tenant_id` 条件，检测方式为 `"tenant_id" in str(whereclause)` 字符串匹配。

### 必须检查（🚨）

- 新增的数据库查询是否在租户隔离覆盖范围内？
  - 简单单表 CRUD → 自动注入可覆盖 ✅
  - 多表 JOIN / 子查询 / 别名 → 自动注入可能失效，必须显式确认
  - `text()` / raw SQL → 完全绕过自动注入，必须手动加 tenant_id
- Insert 操作是否正确写入了 `tenant_id`？
  （自动注入仅覆盖 Select/Update/Delete，Insert 需应用层通过
  `app_runtime_context.get_tenant_id()` 赋值）
- 是否存在通过 ID 直接查询而未校验租户归属的接口？
  （如 `GET /resource/{id}` 未加 tenant_id 过滤）
- 跨租户查询（如管理员接口）是否在 PR 中明确说明了业务理由和权限边界？

### 常见违规模式

```python
# ❌ 危险：raw SQL 绕过租户隔离
session.execute(text("SELECT * FROM projects WHERE id = :id"), {"id": project_id})

# ❌ 危险：子查询中的别名可能让自动注入失效
subq = select(Model.id).where(Model.status == 'active').subquery()
query = select(OtherModel).where(OtherModel.model_id.in_(select(subq.c.id)))

# ✅ 正确：显式加 tenant_id
subq = select(Model.id).where(
    Model.status == 'active',
    Model.tenant_id == app_runtime_context.get_tenant_id()
).subquery()
```

## 三、数据库会话安全

本项目存在两套 DB Session 体系，混用是最常见的事务一致性风险来源。

### 体系识别

| 体系 | 来源 | 适用场景 |
|------|------|---------|
| A（推荐） | `Depends(get_db)` 或 `Depends(get_db_and_user)` | FastAPI 路由，新代码 |
| B（遗留） | `auth_middleware` → `ContextVar` → `BaseMapper` 自动获取 | 遗留路由链路 |
| C（任务专用） | `app.database.base.get_db_session()` | Celery 任务、脚本 |

### 必须检查（⚠️/🚨）

- 同一接口/任务链路中是否混用了两套体系的 session？
  - 路由注入了 `db = Depends(get_db)` 但 service 内部又通过 BaseMapper 从 ContextVar 取 session → 两个 session，事务不一致
- Celery 任务是否使用了正确的 session 来源？
  - 必须用 `from app.database.base import get_db_session as task_db_session`
  - 禁止用 `AsyncSessionLocal()` 直接创建异步 session
- 写操作是否有显式 `commit` + 异常时 `rollback`？
  （不要依赖遗留体系 B 的"请求结束自动提交"行为）
- 导入 `get_db_session` 时是否用了别名区分？
  （`app.database.base.get_db_session` vs `app.utils.db_session_context.get_db_session`）

### 常见违规模式

```python
# ❌ 混用：路由注入了 db，但 service 调 BaseMapper（从 ContextVar 取另一个 session）
@router.post("/resource")
async def create(db: AsyncSession = Depends(get_db)):
    service = ResourceService()
    service.create(data)  # 内部用 BaseMapper，取的是 ContextVar 里的 session
    db.commit()  # commit 的是注入的 session，BaseMapper 的写入未提交

# ❌ Celery 任务用了异步 session
@celery_app.task
def process_task():
    asyncio.run(_process())

async def _process():
    async with AsyncSessionLocal() as session:  # ❌ 事件循环冲突
        ...

# ✅ Celery 任务正确方式
from app.database.base import get_db_session as task_db_session

@celery_app.task
def process_task():
    asyncio.run(_process())

async def _process():
    async with task_db_session() as session:  # ✅ 同步引擎 + AsyncCompatibleSession
        ...
```

## 四、安全审核

### 4.1 注入与路径穿越（🔒）

- 是否存在 raw SQL 字符串拼接（`f"SELECT ... WHERE {var}"`）？
  必须使用 SQLAlchemy ORM 或 `bindparams` 参数化
- 文件路径是否校验了 `..` 穿越？
  特别关注下载/上传类端点的 path 参数
- 外部输入（文件名、路径、URL）是否做了清洗和白名单校验？

### 4.2 敏感信息（🔒）

- 代码中是否硬编码了密钥、Token、密码、内网 IP/URL？
  必须通过 `app/core/config.py` 的 `Settings` 配置
- `os.getenv` 中是否有敏感信息的默认值？
  如 `os.getenv('SECRET', 'default_key')` → 默认值不安全
- 日志/print 中是否输出了 token、密码、密钥、连接串？

### 4.3 鉴权与权限（🚨）

- 新增接口是否正确添加了鉴权依赖？
  - 需要认证：`Depends(get_db_and_user)` 或 `Depends(get_db_and_admin)`
  - 公开接口必须在 PR 中明确说明理由
- 是否存在绕过中间件链的鉴权逻辑（如手动解析 JWT）？
- 管理员接口是否校验了管理员角色？

### 4.4 反序列化安全（🔒）

- 禁止 `eval()`、`exec()`、`pickle.loads()`
- JSON 反序列化必须用 `json.loads()` + Pydantic 校验

## 五、API 规范

### 必须检查（⚠️）

- 路由文件是否在 `app/api/v1/` 下？是否在 `main.py` 中注册？
- 路由层是否只做编排（入参校验、鉴权、调 service、返回）？
  禁止在路由层写复杂业务逻辑、循环、多表事务
- HTTP 状态码是否正确？
  - POST → 201 | DELETE → 204 | GET/PUT/PATCH → 200
  - 不存在 → 404 | 冲突 → 409
- 是否声明了 `response_model`？
- 列表接口是否使用了 `fastapi-pagination` 的 `Page[T]`？
  禁止无 LIMIT 的全量返回
- 错误返回是否与 `app/main.py:validation_exception_handler` 一致？
  面向用户的错误信息使用中文
- Service 注入是否使用了 `@inject` + `Depends(Provide[AutoContainer.xxx_service])`？

### 常见违规模式

```python
# ❌ 路由层写业务逻辑
@router.post("/projects")
async def create_project(data: CreateSchema, db = Depends(get_db)):
    existing = await db.execute(select(Project).where(Project.name == data.name))
    if existing.scalar():
        raise HTTPException(409, "已存在")
    project = Project(**data.dict())
    db.add(project)
    await db.commit()  # 应该放在 service 层

# ✅ 路由层只编排
@router.post("/projects", status_code=201, response_model=ProjectResponse)
@inject
async def create_project(
    data: CreateSchema,
    deps = Depends(get_db_and_user),
    service: ProjectService = Depends(Provide[AutoContainer.project_service])
):
    return await service.create(data, deps.db, deps.user)
```

## 六、数据模型与 Schema

### 必须检查（⚠️）

- 新表 Model 是否继承 `baseModel`？
  （自动获得 id/tenant_id/created_at/updated_at 等基础字段）
- 字段是否使用 `Mapped[...]` 类型注解（SQLAlchemy 2.0 风格）？
- 字段是否有中文 `comment`？状态/枚举字段是否在 comment 中写明取值范围？
- 命名是否符合规范？
  - 字段：`snake_case` | 布尔：`is_xxx`/`has_xxx` | 时间：`xxx_at`
- 是否创建了数据库外键约束？（禁止，应用层维护关联）
- 索引是否在 `__table_args__` 中定义？命名是否为 `idx_{表名}_{字段名}`？
- 按租户查询的表是否考虑了 `tenant_id` 相关索引？
- JSON 字段是否使用了项目的 `ChineseJSON` 类型？（确保中文存储正确）
- Schema 是否继承了 `BaseModelWithTimezone`（时区转换）或 `BaseSchema`？

## 七、Celery 任务与后台处理

### 必须检查（⚠️）

- 任务是否设置了 `soft_time_limit` 和 `time_limit`？
- 重复投递/重试时是否安全（幂等性）？
  - 是否会重复创建资源？重复写入数据？
- 失败场景是否有明确处理？
  - 哪些错误重试？哪些快速失败并报警？
  - 涉及多步外部资源（K8s/存储/镜像）时是否有补偿逻辑？
- DB session 是否使用 `task_db_session`（来自 `app.database.base.get_db_session`）？
- `asyncio.run()` 内部是否避免了异步 session（`AsyncSessionLocal`）？
- 新增任务模块是否加入了 `app/tasks/celery_app.py` 的 `include`？
- 租户上下文是否正确设置？
  （`app_runtime_context.set_tenant_id()` 在任务执行前调用）

## 八、配置与环境变量

### 必须检查（⚠️）

- 新增配置是否同步更新了 `app/core/config.py` 和 `env.example`？
- 业务代码是否直接使用了 `os.getenv()`？
  必须通过 `from app.core.config import settings` 访问
- `os.getenv` 的默认值是否包含敏感信息？
  如 `os.getenv('SECRET', 'default_key')` → 不安全
- 生产必填配置是否有启动时校验（缺失时 fail fast）？

## 九、性能审核

### 必须检查（⚡）

- 循环中是否存在逐条查询数据库（N+1）？应批量查询或 `joinedload`
- 是否存在无 LIMIT 的大表查询？
- 循环中是否存在网络请求、文件 IO、K8s API 调用？
- 文件句柄、HTTP 客户端、DB 连接是否正确关闭？
  （优先使用 `async with`、`try/finally`）
- 大文件操作是否使用了流式处理而非全量加载？

## 十、代码质量

### 必须检查（⚠️/💡）

- 是否残留 `print()` 语句？应使用 `logger`（项目用 loguru）
- 是否有裸 `except:` 或 `except Exception` 而未记录日志？
  必须用 `logger.exception()` 或至少 `logger.error()`
- 新增/修改函数是否有参数和返回值类型注解？
- 异常是否被吞掉（catch 后 pass/return None 而不上报）？
- 单个函数是否超过 80 行？是否应拆分？
- 是否存在明显的复制粘贴代码？应提取公共方法
- 面向用户的提示文案是否为中文？
  建议使用 `app/utils/error_messages.py` 中的统一方法

2. 每个问题包含：文件路径、行号（或行范围）、问题说明、修复建议
3. 级别标注：🚨 阻塞 | 🔒 安全 | ⚡ 性能 | ⚠️ 重要 | 💡 建议
