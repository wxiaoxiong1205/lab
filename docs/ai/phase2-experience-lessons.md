# 第二阶段开发经验与反思

> 本文档是第二阶段长期维护的经验库。它不是第一阶段生产环境复刻清单，也不是泛泛复盘；它用于后续每轮开发前快速校准方法，减少重复探索、重复返工和“看起来完成但业务链路没闭合”的问题。

## 1. 总原则

- 以当前仓库已验收实现为基线，不默认回到第一阶段“先全站对齐生产环境”的模式。
- 用户当前明确需求、截图、批注和交互说明优先于历史文档；只有用户明确要求时才重新看生产环境。
- 浏览器批注不是只改视觉。凡批注涉及按钮、状态、跳转、保存、删除、提交、筛选、权限或数据引用，必须验证真实点击链路和状态变化。
- 涉及页面功能、字段、状态、布局、信息架构或交互变化时，必须同步更新页面内嵌设计文档基线。
- 涉及跨页面实体、权限、状态或任务引用时，优先查 `src/services/`、共享 store、任务状态 helper 和已有 API 边界，避免在页面里重写一套孤立 mock。
- 每轮收尾至少确认：页面可访问、关键操作可点击、状态符合预期、文档同步、构建通过；若不满足，必须明确风险和阻塞。

## 2. 重复犯错点

### 2.1 过度回到生产环境

- 症状：用户只提当前迭代需求时，仍然机械地先按生产环境做差异拆解，导致实现方向受历史截图或旧生产逻辑干扰。
- 根因：把第一阶段复刻方法当成永久默认流程，没有及时切换到第二阶段真相源优先级。
- 后续规则：每轮先判断用户是否明确要求“看生产环境 / 对齐生产环境”。没有明确要求时，以当前仓库和用户本轮需求为准；若引用历史资料，必须标注为历史背景。

### 2.2 只画 UI，未闭合操作链路

- 症状：页面看起来接近截图，但点击按钮无效，或只弹 toast，不更新数据、状态、进度、按钮禁用、跳转和后续页面。
- 根因：把“视觉还原”误当成交付完成，没有从用户任务流角度验证保存、完成、提交、删除、审核、启动、停止等动作。
- 后续规则：凡新增或调整操作按钮，都必须写清“点击前状态 -> 点击动作 -> 数据变化 -> 页面反馈 -> 下一步可做什么”。开发后至少在浏览器里点一遍主链路。

### 2.3 未优先复用共享状态

- 症状：同一数据、模型、推理服务或任务在不同页面显示不一致；删除、改名、引用保护只在单页生效。
- 根因：页面内部直接维护局部数组或临时 mock，没有先检查共享 store、API 层和引用保护工具。
- 后续规则：涉及数据集、模型、在线推理服务、在线标注服务、任务引用、权限和项目上下文时，先查共享服务层；局部 mock 只能用于未接后端的演示，并要明确边界。

### 2.4 页面内嵌设计文档滞后

- 症状：页面已经多次迭代，但右侧需求文档仍描述旧字段、旧按钮、旧流程，后续 AI 又按旧文档返工。
- 根因：把 `pageDocs.ts` 当成附属说明，而不是运行态协作基线。
- 后续规则：页面功能、字段、状态、布局、路由、交互、信息架构变化，都同步更新对应文档；如果发生结构变化，必须写清“旧结构 -> 新结构”。

### 2.5 浏览器验证不足

- 症状：构建通过，但页面运行态仍有按钮错位、下拉不可选、地址跳转错误、分页/进度异常或已完成状态仍可编辑。
- 根因：只依赖静态阅读和构建，未用浏览器验证用户实际路径。
- 后续规则：涉及可视化和交互的需求，构建之外必须打开目标路由做最小操作验证；如果浏览器工具不可用，要说明未验证的具体风险。

### 2.6 部署路径和环境命令误用

- 症状：Vercel 从错误目录执行导致 Root Directory 被拼成双层路径，或本地服务端口、项目路径判断错误。
- 根因：没有先检查 `.vercel/project.json`、仓库根目录、应用目录和当前工作目录。
- 后续规则：部署前确认 `git status`、`git rev-parse --show-toplevel`、`.vercel/project.json`、应用目录和远端 SHA；Vercel 项目若 Root Directory 已配置为 `fastdata-llm-training`，应从仓库根目录执行生产部署。

### 2.7 敏感 token 处理风险

- 症状：用户临时提供 Vercel token 或内部链接时，容易被复制进命令历史、脚本、配置或文档。
- 根因：急于完成部署，没有把“临时使用、不落盘、不入提交”作为硬约束。
- 后续规则：所有 token、账号、内部链接只用于临时核对；不得写入代码、配置、日志、文档或提交信息。能使用已登录 CLI 时优先使用现有登录态。

## 3. 做得好的地方

- 第二阶段真相源优先级已经建立：用户当前需求和当前仓库基线优先，历史生产环境资料降级为背景材料。
- 页面内嵌设计文档成为有效协作资产：当页面功能和文档同步时，后续返工更少，需求上下文更容易被继承。
- 数据服务沉淀了共享 store、API 层、最小本地后端和引用保护思路，适合作为跨页面数据联动的复用模板。
- 任务型模块开始形成状态机意识：启动、运行、终止、完成、失败、重新提交、删除等动作需要统一判断，不应散落在页面里。
- 路由和壳层优先的策略有效：涉及导航域、项目上下文、沉浸式页面时，先处理壳层和路由，再处理页面细节，返工成本更低。
- Vercel 发布闭环已经跑通：本地构建、GitHub 推送、Vercel 生产部署、生产域名回传形成了可复用流程。
- 用户浏览器批注驱动迭代效率高：批注定位具体元素和上下文后，能快速收敛字段、按钮、交互和状态问题。

## 4. 可复用资产

- 第二阶段工作流：读 `AGENTS.md` -> 读相关代码和文档 -> 判断需求源 -> 定影响范围 -> 开发 -> 同步页面文档 -> 构建和浏览器验证 -> 汇报风险。
- 页面文档基线：`fastdata-llm-training/src/docs/pageDocs.ts`。
- 权限和项目上下文：`src/services/permissionStore.ts`、`src/services/permissionCatalog.ts`。
- 数据服务共享层：`src/services/dataServiceStore.ts`、`src/services/dataServiceApi.ts`、`server/dataServiceServer.mjs`。
- 任务状态规则：`src/services/taskLifecycle.ts` 及各任务型页面中已经沉淀的状态操作约束。
- 引用保护模式：数据、模型、在线推理服务、在线标注服务被任务引用时，不应只在删除按钮上做表面禁用，要能说明引用链和释放条件。
- 运行与发布手册：`docs/runbooks/development.md`、`docs/runbooks/validation.md`、`docs/runbooks/deployment.md`。

## 5. 模块级经验

### 5.1 数据服务

- 版本、创建人、数据明细、单条删除、引用保护和跨页面同步是核心，不是列表字段的装饰。
- 新增版本必须能体现版本递增和样本继承，否则只是视觉假版本。
- 数据集选择弹窗、字段回显、清洗/标注/评估引用应尽量复用同一数据源和同一选择体验。

### 5.2 Notebook

- 大模型 Notebook 和机器学习 Notebook 经常需要保持行为一致，但数据来源、模型来源和 AI 服务来源可能不同；开发时要先区分“共性交互”和“差异字段”。
- 停止、启动、编辑配置、保存环境、发布案例、查看详情等动作要按状态控制，不应只隐藏或展示按钮。
- 运行中与停止后的可编辑范围不同。涉及资源、镜像、AI 服务、显卡配置时，必须明确是否需要停机、保存后何时生效、再次启动前是否可反复编辑。

### 5.3 大模型训练

- 训练创建页和详情页字段必须保持口径一致，尤其是模型选择、训练加速、资源配置、数据集格式和版本详情。
- 复杂配置不宜只堆字段；需要明确默认值、开启条件、说明信息和与后续详情页的展示关系。
- 训练任务名称、描述、版本级描述等概念要避免混用。

### 5.4 机器学习数据管理与标注

- 不同标注类型不是同一个表单换标签：文本分类、实体识别、图像分类、物体检测、图像分割都需要不同工作台和不同操作反馈。
- 标注页最容易犯“UI 有了但不能标注”的错误。必须验证选择标签、AI 自动标注、完成标注、跳下一条、提交标注、删除当前数据、已完成锁定。
- 多人标注要区分任务总览、标注任务、审核任务。创建者看进度，标注者做标注，审核者做审核，不应共用同一个详情页。

### 5.5 效果评估

- 自动评估、基准评估、人工评估虽然都叫评估，但详情结构、报告结果、数据明细、日志和下载操作不同。
- 图表形式变更不仅是换组件，还要检查基准评估和人工评估是否都同步、数据为 0 时是否仍可读。
- 结果集、待评估模型/服务、报告下载之间存在引用关系，不能只在当前页展示静态文本。

### 5.6 系统管理

- 集群、存储、镜像、基础模型等系统管理模块通常是平台级，不依赖项目上下文；不要套用项目内业务路由规则。
- 编辑表单新增字段时，要同步查看详情、列表摘要和二次编辑回显。
- 存储类型、镜像类型这类枚举变化要检查创建、编辑、详情和筛选是否一致。

### 5.7 部署发布

- 提交前先确认工作区差异，避免把无关修改混入提交。
- 推送前确认本地 HEAD 与远端分支关系，避免重复提交或以为有改动但其实工作区干净。
- Vercel 部署前确认项目绑定和执行目录；部署后记录生产 URL、Inspect URL、构建结果和 warning。

## 6. 每轮开发门禁

### 6.1 开工前

- 已阅读 `AGENTS.md`。
- 已判断本轮是否需要参考生产环境；没有明确要求时，不默认回到生产环境。
- 已阅读相关页面、组件、服务、路由和页面文档。
- 已检查是否有可复用共享状态、组件、选择弹窗、状态机、引用保护或 runbook。
- 已确认工作区是否有无关未提交改动。

### 6.2 开发中

- 先处理路由、壳层、状态和数据边界，再处理页面细节。
- 批注涉及操作时，必须按真实链路实现，不只改文案、样式或按钮显示。
- 不把临时 token、账号、内部链接写入仓库文件。
- 对临时 mock、未接后端、仅演示逻辑明确标记。

### 6.3 收尾前

- 页面文档已同步。
- 目标路由已打开验证。
- 关键按钮已真实点击验证，包括保存、完成、提交、删除、启动、停止、编辑、下载等本轮涉及动作。
- `npm run build` 通过；若只改纯文档，可运行 `git diff --check` 并说明无需构建。
- Git 提交前再次确认 `git diff --stat` 和 `git status --short`。

## 7. 后续自进化规则

- 每次出现同类返工，要把“返工原因”和“新规则”补回本文档，而不是只修当前代码。
- 每次用户指出“还是不生效 / 没对齐 / 跟之前一样错”，优先检查是否违反了本文档的门禁，而不是马上堆新 UI。
- 复杂模块迭代前先读对应模块级经验；如果经验不够，先补充发现，再开发。
- 如果某个规则连续三次被证明有效，应考虑升级到 `AGENTS.md` 或对应 runbook；如果只是某模块局部经验，留在本文档即可。
- 经验库必须保持可执行：少写口号，多写触发条件、检查对象和必须验证的动作。
